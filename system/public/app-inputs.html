MIDI & independent app input

Hosts enable MIDI & app-only input before or during a session. Guests open Controllers, then select MIDI devices or turn on app-only keyboard and mouse events. Video is optional.

What receives the input?

App-only input preserves a separate guest and device identity. It does not move the host’s system mouse, type into desktop apps, or create extra Windows/macOS/Linux keyboard or mouse devices. A game needs an integration to use these events as separate players. Existing controller mappings still provide ordinary virtual gamepad input.

MIDI devices

Click Find MIDI devices and allow browser MIDI access. Select each input to share. Web MIDI needs a supported browser on localhost or HTTPS. Note, pressure, pitch, controller, program and clock messages stream without audio buffering; SysEx and device-programming messages are excluded.

The host can select an existing MIDI output under MIDI output & app integration. To route into another program, expose a virtual MIDI port using that operating system or another MIDI tool. WebRTC Pad does not install a virtual MIDI driver. Programs listening to that port can recognize the MIDI. Sharing an output also shares its MIDI channels.

Read the local app stream

During the call, the host clicks Copy local app connection. This copies a private read-only WebSocket URL for that session. Connect from an app on the host computer. It expires when the session ends. There is no stored input history.

const socket = new WebSocket(copiedConnectionURL);
socket.onmessage = ({data}) => {
  const event = JSON.parse(data);
  if (event.type === 'reset-all') return releaseAllDevices();
  if (event.type === 'snapshot') return event.devices.forEach(consumeInput);
  if (event.type !== 'input') return;
  // Keep each peerId + device separate. Never merge into the OS pointer.
  if (event.kind === 'reset') releaseDevice(event.peerId, event.device);
  else consumeInput(event);
};
socket.onclose = () => releaseAllDevices();

Every input has version: 1, peerId, device, kind and seq. Keyboard events contain a complete keys array of physical key codes. Mouse events contain normalized x/y, complete buttons, pixel dx/dy, wheelX/wheelY, source width/height and sourceId. MIDI events contain data bytes and a device label. Coordinates refer to the selected view’s content, excluding letterboxing. An input pad without video uses reported host dimensions, or 1920 × 1080 if none are available.

Release held state on reset, disconnect or timeout. Do not persist raw keys or MIDI without the participants’ agreement. A slow local consumer is disconnected rather than given stale input. Local bridge events have the same schema as the webrtc-pad-input CustomEvent dispatched on the host page’s document.

Local API server and SDK

The normal Start launcher also runs the local input API. GET /api/inputs lists the API version, supported input kinds and active local session IDs without exposing credentials. The API uses the same local port as the app (8787 by default). It stays loopback-only.

POST /api/inputs/sessions with JSON {"label":"My app"} creates an input session and returns id, readToken and writeToken. Connect readers to /api/inputs/subscribe?session=ID&token=READ_TOKEN and the single publisher to /api/inputs/publish?session=ID&token=WRITE_TOKEN. Publishing uses the input schema described above, including peerId. Send {"type":"heartbeat"} at least once a second while connected; the included publisher SDK does this automatically. A stalled publisher is reset and disconnected after three seconds so held inputs cannot remain stuck. Readers cannot publish or emulate devices. A publisher closing sends reset-all; deleting a session releases and closes its readers. Delete with DELETE /api/inputs/sessions/ID and header Authorization: Bearer WRITE_TOKEN.

Native apps can manage local sessions. Browser management and publishing require the app’s own origin. A web app on another origin can read only when explicitly given a private read URL; it cannot create sessions or inject OS inputs. Do not share either token publicly.

For a simpler integration, import the standalone SDK and pass the connection copied from the host or the guest receiver:

import { InputClient } from 'http://localhost:8787/input-api.js';
const inputs = new InputClient(copiedConnectionURL);
inputs.addEventListener('snapshot', e => {
  for (const device of e.detail) consumeInput(device);
});
inputs.addEventListener('input', e => consumeInput(e.detail));
inputs.addEventListener('reset', () => releaseAllDevices());
inputs.connect();
// inputs.devices contains the latest independent device states.
// inputs.close() clears state and disconnects.

Controller events use kind: "controller", a complete normalized state.buttons and state.axes, and a device identity. Axes lx/ly/rx/ry range from −1 to 1; triggers lt/rt range from 0 to 1. Apply reset events and connection loss to release held inputs. Snapshots contain current device state, never an input history; MIDI note messages are not replayed to new readers.

Guests receiving host controllers

The host opens Share my controllers with guests, enables sharing and selects physical controllers. Guests open Controllers → Advanced → Receive host controllers, opt in, then choose an endpoint. App-only input API creates no OS device; its copy button connects a compatible local app. Native endpoints create virtual gamepads using the installed platform backend. Missing drivers produce an actionable error rather than an automatic driver installation.

Native receiving pauses outgoing controller sharing and releases local blocking to prevent feedback loops. App-only receiving keeps outgoing controller sharing available. Received controllers are never automatically selected for forwarding. Turning receiving off, revoking host sharing, disconnecting or changing roles releases the receiver. After a role change, enable receiving again explicitly. Native XInput is limited to four indices; other supported endpoints retain their own limits.

Desktop control stays separate

For normal remote desktop operation, use the host’s Keyboard & mouse access controls. Enabling an app-only input on the guest disables that guest’s corresponding desktop input toggle. Browser sharing needs focus and prevents supported page actions. Windows shortcuts may still act locally. MIDI input can remain active in the background.
