Connect across networks.

Invite accepted, but connection failed?

Manual pairing needs both files: the guest opens the invite, sends their reply back, and the host opens that reply. Keep both apps open. An invite expires after 10 minutes.

If the guest still shows Failed after the reply is opened, expand Why did it fail? under that guest. It shows whether each computer found a relay route, without displaying private connection details.

A TURN relay carries your controller, video and audio traffic when the two networks cannot connect directly. Free STUN servers only discover direct routes. A WebSocket server automates setup; it does not replace TURN.

If TURN is configured, try setting ICE_TRANSPORT_POLICY=relay in the host's .env, restart the app and exchange fresh files. This tests relay-only access; return to all afterward to allow direct connections. If it still fails, compare both computers' relay routes and check TURN credentials, service quota, VPN and firewall restrictions.

Want a join link and automatic replies?

Run 10-Run-Invite-Server from your platform's shortcuts folder and publish it at a trusted HTTPS address. Set SESSION_SERVER_URL=https://your-invite-server.example in both local apps and restart them. The host can then create a session link and accept join requests. Setup instructions: system/docs/invite-server.md.

Save a diagnostic file

On the host, open Settings & troubleshooting → Connection setup → Save connection diagnostics, or expand Why did it fail? under the guest and click Save diagnostics. On the guest, open Connection settings → Save connection diagnostics.

Ask each person to save their file after the failed attempt. The JSON files include connection states, a short timeline, relay discovery, server error codes, browser/OS family and available traffic measurements. They exclude IP addresses, server URLs, credentials, names and input contents. Files stay available after leaving a session; save them before refreshing or closing the page.

Firefox and manual file pairing

Firefox can time out while a reply file is being sent back, even when both computers have relay routes. For manual invite/reply files, use Chrome, Edge or Brave. A hosted session link exchanges connection details automatically and is the recommended Firefox workflow. This timing issue is separate from TURN configuration; see Mozilla’s report about delayed answer exchange.

Creating a manual invite starts its download automatically. Opening that invite creates and downloads the reply automatically. Send the downloaded file through your chat app; use Save again if another copy is needed.

Optional: recover dropped connections

If a connection drops completely, a forwarded port lets your apps find each other again. Everyone still runs their own local app and exchanges invite/reply files to join.

Only the host needs this setup. Your screen and controls still use WebRTC. Keep your TURN settings for networks that need a relay.

  1. Give the host a stable home address

    Reserve its LAN address in your router, such as 192.168.1.50. Set up a DNS or dynamic-DNS hostname pointing at your router's public IP.

  2. Enable the fallback

    Merge these settings into the host's existing .env. Replace the example hostname with yours and keep your relay credentials.

    HOST=127.0.0.1
PORT=8787
PUBLIC_URL=https://play.example.com
SIGNALING_FALLBACK=1

    The project includes system/config/port-forwarding.env.example.

  3. Run the secure connection helper

    Install Caddy. Change the hostname in system/config/Caddyfile, then run this from the project folder:

    caddy run --config system/config/Caddyfile

    Keep Caddy running. It handles the trusted HTTPS certificate and exposes only the fallback connection.

  4. Forward two router ports

    Forward TCP 80 → host port 80 and TCP 443 → host port 443. Allow Caddy through the host's firewall on those ports. Leave port 8787 unforwarded.

  5. Restart, then send fresh invites

    Restart Node, open your app at http://localhost:8787, and check the fallback status in host settings. Create a new invite for each friend. Their connection settings will show when the fallback is connected.

Check it outside your home network

On a phone using cellular data, open your public HTTPS hostname. You should see a signaling message with a valid certificate. Then try pairing with a friend outside your LAN.

If your ISP uses carrier-grade NAT, ordinary router forwarding may be unavailable. Ask for a public IP or use a separately reachable secure signaling endpoint.

Browser reloads still need fresh invitations. Keep Node, Caddy, and the host browser running throughout the game.

More details and troubleshooting: system/docs/port-forwarding.md in the project download. The restricted public endpoint does not serve a join webpage.

Run your own STUN/TURN relay too

Yes, the host can run coturn alongside this app. Install Docker, then generate private settings using your real hostname and public IP:

npm run setup:turn -- --hostname turn.example.com --public-ip 203.0.113.10

The example IP is a placeholder. Merge .local/coturn/app.env into your .env, then start the relay:

docker compose -f system/config/coturn.compose.yml up -d

Forward UDP and TCP 3478 plus UDP 49160–49359 to the relay computer with the same internal port numbers. Allow these ports in its firewall. Keep the generated master secret private. Restart the app and create fresh invites.

This is separate from Caddy’s recovery socket. It requires a public reachable address; carrier-grade NAT can prevent home hosting. Docker Desktop adds a NAT boundary, so test from outside your LAN. Full instructions, NAT settings and troubleshooting: system/docs/self-hosted-turn.md in the download.
