Set up your Mac

Native sharing requires macOS 13 or later. Controller-only play and browser sharing are available without the native capture helper.

1. Prepare native sharing

Run mac/shortcuts/07-Host-Native.command from the downloaded app folder. It builds the Mac helper and starts the app. If setup asks for Apple Command Line Tools, install them with xcode-select --install, then run the launcher again. Install FFmpeg separately, for example brew install ffmpeg if you use Homebrew.

Setup does not capture your screen or grant permissions.

2. Allow screen and playback audio

Choose the button below to request Screen Recording permission. In System Settings → Privacy & Security, allow the helper or terminal macOS identifies. On newer macOS versions this is named Screen & System Audio Recording. Reopen the app if macOS asks, then refresh the source list.

Choose a window for that window’s video and its app’s audio, or the main screen for system playback audio. App audio includes its other windows; it does not include unrelated apps or your microphone. Audio stays off until you enable Include native audio.

3. Allow desktop input only if you need it

To share a mouse or keyboard, allow Accessibility for the helper or terminal macOS identifies. Then enable the guest permissions in the host app. Controller play does not need Accessibility.

Window-only control follows the selected window and blocks clicks when another app covers it. Keyboard input requires that window to be focused. Some games and apps do not expose enough Accessibility information; those windows cannot use restricted control. Entire-screen control requires a separate host confirmation.

Cursor markers and fullscreen

Enable desktop cursors in guest settings to see each guest’s color over other apps. Markers do not take focus or intercept clicks. They may appear in shared video. Exclusive fullscreen games, secure dialogs and protected content can hide overlays or block capture/input.

Checking the helper…

Mac native hosting is experimental. The helper uses Apple’s public APIs; real capture, audio and mouse behavior still need validation on Mac hardware. Native virtual controllers have separate platform requirements.

Receiving controllers and local app input

The native controller endpoint uses a separate virtual HID helper, built for Intel or Apple Silicon by Start-Mac.command. macOS may require Apple-approved virtual HID signing or entitlement; Screen Recording, Accessibility and Input Monitoring do not grant that entitlement. If macOS denies device creation, choose App-only. The local input API and separate keyboard/mouse streams need no virtual HID permission. MIDI depends on browser support; a supported Web MIDI browser can select devices without installing a virtual HID driver.

A custom signed MACOS_HID_HELPER is preserved. Setup does not bypass signing or change system security. Native receiving pauses outgoing controller sharing; stopping or disconnecting releases its virtual pads. Mac capabilities and protocol paths have fixture tests; native device creation still needs validation on an appropriately signed Mac.
