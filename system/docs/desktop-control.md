# Optional desktop mouse and typing

Gamepads and keyboard-to-controller mode are independent of screen sharing. Every assigned guest gets their own virtual controller. Desktop mouse and typing are separate features, both **off by default** for every new host session.

1. Choose a window or screen under **Screen sharing**, or leave it off for a video-free mouse pad. Open **Keyboard & mouse** before starting. Desktop control defaults to **Off**. To grant access, choose **Shared window only** for a verified window or **Entire desktop**. Read the in-page **CAUTION** message. Mouse and typing start checked; turn either off to exclude it. These permissions begin only after **Start a session**. During a session, the same controls are in **Settings → Guests & access**.
2. After joining, guests open **Controllers → Advanced → Mouse & desktop controls**, enable the mouse and/or **Type on the host desktop**. To use a keyboard as a gamepad instead, choose **Use keyboard & mouse as a controller** in the guest controller panel; this requires no desktop-typing permission.
3. The host can revoke input with **Stop desktop control**. Ending the session also revokes it. Changing sources keeps the chosen mode and mouse/typing options, releases held input, and binds access to the new supported source. Window-only mode pauses input for whole-screen or unverified sources. Stopping a shared-window stream revokes its access; explicitly approved desktop control can continue as a mouse pad with video off.

Without video, the guest's picture area becomes a **Remote mouse pad** for the approved surface. A shared window uses its live client-area size and position; full-desktop permission uses the primary display. Dimensions are reported on connect/change, and resizing or fullscreening the picture preserves normalized mapping. Window-only input is enforced by the Windows native helper: it pins HWND plus process identity, maps into the live window rectangle, rejects covered/minimized targets, and revokes when the window closes. Moving/resizing the window does not broaden access. Choosing another shared source releases held input and binds control to that source within the selected scope.

Native capture on Windows is the reliable path for binding video and input to one selected window. Browser window capture is bound only when its reported identity uniquely matches an enumerated Windows window. Otherwise window mouse input stays unavailable; use Native capture, or separately grant full-desktop access and turn video off to use the desktop pad. Linux X11 also enforces selected-window identity, live bounds, occlusion and keyboard focus. macOS 13+ uses the Swift helper with strict public Accessibility window checks; an unidentifiable window is denied and full-screen control needs separate permission; Wayland native input is disabled. See [Linux setup and scope checks](linux-desktop.md).

**Guest pointers · no desktop control** is independent of desktop access and defaults off. The host can enable it when needed. Guests, including spectators, can move their own colored markers and show click feedback on the shared picture or pointer pad while Desktop control remains Off. These messages never reach the OS input injector, move the system pointer, or click applications. Multiple guest pointers stay independent. Optional labels are controlled by the host. Markers appear in the call, including fullscreen, and over a verified main shared window/screen on supported hosts. They do not appear in video-only Picture-in-Picture. Pointer traffic stops when the host turns this option off or the guest leaves the pointing surface.

Real mouse control remains a separate host and guest permission. It uses the host's shared system pointer and can still display the guest's colored marker. Several guests using real mouse control can compete for that one pointer; visual-only pointers do not. An application could explicitly integrate the separate pointer messages to support independent interactions, but ordinary desktop apps do not receive them as clicks. No app-specific pointer adapter is included.

Desktop input uses the OS's shared mouse pointer and keyboard state. It does not create separate physical mice/keyboards. Colored pointers are app overlays, while keyboard-to-controller mode does produce separate gamepads. Multiple guests' held keys/buttons are combined so one guest releasing a key does not release another guest's hold. A device-aware application could support independent mice using a future Raw Input/virtual HID integration; that backend is not included.

Typing requires the app to have focus and skips text fields/settings controls. Browsers reserve some system shortcuts. Click/drag inside the mouse pad or matching stream, and use the wheel for scrolling. Loss of focus, reassignment, pause, disconnect, host revocation, and stale input release held keys/buttons. Reliable ordered messages carry key/button state; an independent native watchdog releases holds if the Node/browser path stops.

The host needs Python 3 (set `PYTHON` in `.env` for a custom executable). Joining computers do not need Python. Windows uses SendInput and cannot control elevated applications from a non-elevated host. Linux currently needs X11, libX11 and libXtst; Wayland input is not implemented. macOS uses the compiled Swift helper and needs Accessibility authorization for the helper or terminal identified by macOS. See [Mac setup and validation limits](macos-desktop.md). macOS/Linux desktop injection has not been hardware-validated here. Missing prerequisites are reported when the host enables access; controller/video features remain usable.

Browser/Node tests exercise mouse-pad coordinates, resize metadata, click/scroll/typing state, release, permissions, fullscreen and colored cursors over real local WebRTC with a recording desktop backend. They do not inject clicks or typing into the user's desktop. Real Windows acceptance tests now stream native WGC video and send guest clicks through WebRTC/SendInput into two harmless test windows. They verify window clicks, live move/resize mapping, overlapping-window rejection, the additional full-screen grant, and revocation. macOS/Linux OS injection remains unvalidated here.

For local development, `npm run demo:local -- --mouse` starts two separate Node apps and browser windows, pairs them through files, and uses a simulated 1920×1080 desktop. Its crosshair, button/wheel/key readout and colored cursor show input travelling to the host and back through encoded video. Video can be turned off to test the mouse pad. Mouse and typing are recorded by the demo backend; they never enter the OS. Controller checks still use the actual host virtual-controller backend. This optional test harness requires Playwright, Edge (or `BROWSER_CHANNEL`) and the host controller prerequisites; it is separate from normal installation/launch. Closing either demo browser stops both test apps. The regular app continues on port 8787; demo host/client use 8788/8789.

The simulated demo disables desktop cursor overlays and reports its scope to both browsers. Its cursor remains clipped to the test-screen area when scrolling. A persistent demo badge and mouse-control labels distinguish simulated input from real desktop access. No window permission can convert the demo's recording backend into OS input.

To grant real mouse access, use the normal host app: **Settings → Guests & access → Allow guests to control my system mouse**. The guest enables **Control the host's system mouse**. They send input from their focused video/mouse-pad area. **Guest pointers · no desktop control** only controls visual markers; it grants no input permission and does not create an independently clickable OS cursor.


## Desktop cursor overlay and preview

**Guest pointers · no desktop control** controls the in-call markers and supported desktop overlays. It works without mouse or keyboard access. The native overlay starts only for a verified, uncropped main shared source (or separately approved full-desktop mouse control), and stops when pointers are disabled. Unsupported/cropped sources keep in-call pointers. Labels remain optional. A Python/tkinter helper renders tiny transparent, topmost windows with Win32 click-through/no-activation styles. There is no fullscreen browser and no extra Electron runtime. Cursors fade after four seconds without updates and are removed on disconnect or session end. Labels are off by default and follow the host's label toggle.

The overlay follows the primary desktop, or the client area of `NATIVE_WINDOW_HANDLE` when configured. A minimized target hides its markers. Windows capture exclusion prevents the desktop marker from being encoded again where the capture API honors it; each browser renders its own received cursor markers. Windowed/borderless games work with normal desktop composition. Exclusive fullscreen and elevated/secure desktops can cover or block an ordinary overlay. This does not create separate OS mouse devices, separate click focus, or independent game pointers. Window-only input now follows the selected window’s live client rectangle; the no-video pad follows the approved window or primary desktop scope.

Desktop overlays support Windows, Linux X11 and macOS 13+ (experimental). Windows needs Python with tkinter; Linux uses Python with Xlib/Shape and needs no tkinter. Linux and Mac overlays can appear in captured video. Mac uses nonactivating, click-through AppKit panels. Wayland retains in-app cursors. Failures are reported without stopping video or controller input.

**Show my screen preview** detaches/pauses only the local video. **Pause my preview when I switch away** does the same on blur/hidden state and restores on focus. Native preview closes/reopens its local receiving peer; guest encoding continues as needed. Browser capture remains active for guests. Source capture and guest encoder work are not stopped by this preference.

Win32 behavior: [layered window click-through](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features), [capture exclusion](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).


The **Play together (keyboard & mouse)** guide walks both sides through mouse and desktop-typing approval for a game. **Control a computer** uses the same separately approved input features for general desktop access. These inputs share the host’s system mouse/keyboard; keyboard-as-gamepad play is available separately through **Use keyboard & mouse as a controller**.


## Tiled views and selected areas

Layout icons appear only when the host shares multiple views. Grid, side-by-side, stacked top/bottom and featured layouts work inside fullscreen. Single-view mode has previous/next arrows and the current window name. Select a tile before using its approved mouse or keyboard controls. Switching tiles releases held input; messages from an earlier selection cannot target the next window.

For each additional native window, the host can choose **Allow window control**. The native helper binds that approval to that window’s identity. Covered pixels cannot click the covering app; typing is accepted only while the approved window is in front on the host. Browser-picked additional views and independent pop-outs remain viewing surfaces. **Stop desktop control** revokes approvals for all windows immediately.

On Windows, cropping a native window also bounds mouse movement/clicks to that rectangle. Resizing a cropped window revokes input; select the source/area again to renew approval. Keyboard focus is restricted to the window, not to individual controls inside the rectangle. Windows desktop-switch shortcuts are rejected in window mode. Cropped whole-screen and browser shares, and cropped Linux/Mac shares, keep desktop input disabled. This uses the host’s shared OS pointer and keyboard; it is not a security sandbox for untrusted guests.
