# WebRTC Pad

Recognize remote gamepads or mouse/keyboard as native gamepads or remote desktop controls through private Peer2Peer calls. Play split-screen without Netplay or Steam Remote Play, etc. A full call/streaming interface is included via WebRTC (fully encrypted, P2P), Video and audio streaming is optional. Works likes a free, minimal Parsec alternative. 

Each computer runs this local Node app and opens it in a browser. Host and guest share handshake files to establish connections, no third party socket server required. Includes optional remote hosting settings with game room and temp user id support, or self-hosting TURN servers (or use Metered's Open Relay for free).

Built for low controller and video latency using native capture tools as browsers won't cut it, still working out some kinks but it's playable.

Tested on Windows with Diddy Kong Racing N64. Linux and Mac support included but untested. Note Firefox times out handshakes after 45 seconds, so Chromium-based browsers (e.g. Chrome, Brave) are recommended.

## Start here

Extract the entire ZIP into a writable folder. Run the start script for your computer from that main folder:

| Platform | Start the app |
| --- | --- |
| Windows | `Start-Windows.cmd` |
| Linux | `sh Start-Linux.sh` |
| macOS | `Start-Mac.command` |

Each shortcut installs missing dependencies and then starts the app. Later launches skip completed setup. Missing Node is installed automatically where supported. Keep the console and browser open while playing. This runs a normal Node process; it does not install a standalone app EXE.

Windows hosting uses ViGEmBus. Linux hosting needs Python and `/dev/uinput` permissions. Mac hosting uses an experimental HID backend; Mac guests joining other hosts need no driver. See [installation and prerequisites](system/docs/install.md).

With Node already installed, use `npm run host` or `npm run join`; `npm start` reuses your saved choice. Add `-- --no-browser` to print the address without opening it.

The app automatically remembers the last Host/Join page, picture/sound settings, guest-sharing permissions, controller setup choices, and camera/screen quality limits in this browser. The host setup has **Start session** buttons at both the top and bottom. A remembered native source is selected again when it is uniquely available; capture starts only after you choose preview or Start. Browser shares reopen the sharing dialog. Missing windows and changed crop dimensions require a new selection. Microphones, cameras and desktop access stay off until explicitly enabled. Named **Saved setups** remain available for switching between configurations. Host/Join shortcuts and invitation links override the remembered opening page.

For Windows cleanup, close the app and run `windows/shortcuts/99-Uninstall.cmd`. Basic cleanup keeps settings and drivers. Other choices remove local settings, HidHide controller blocking, Interception keyboard/mouse blocking, or both blocking drivers. The menu names every driver being removed or kept; ViGEmBus host virtual controllers are kept. See [uninstall options](system/docs/uninstall.md).

## Connect in three steps

1. **Host:** Start without choosing a source for controller-only play, select a window/screen to include video, or turn on **Share audio only** and choose a sound source. **Include audio** is on by default; browser capture still requires audio approval in its sharing dialog. Click **Start a session**, create an invite with **Play** or **Just watching** access, and use **Create invite file** or **Copy invite text** to send it to your guest. Both use the same invite; **New invite** prepares one for another computer.

2. **Guest:** Open the invite file or click **Paste invite text**. Send the reply file or copy the reply text back. The host opens the reply file or clicks **Paste reply text** to connect you.

3. **Players:** Connect controllers by USB or Bluetooth, then press a button on each one you want to use. You can also select a controller’s card before connecting to have it join automatically. **Map** changes its buttons; **×** removes it from the session. Keyboard players click **Use keyboard & mouse as a controller**. The host assigns the joined gamepads in the game's controller settings.

The call bar keeps microphone, camera, sharing/sound, controller setup, fullscreen and leaving within reach. Starting and ending a session show their progress on the buttons. Pending screen or microphone setup can be cancelled. Stopping a share clears local capture immediately while the session and controller connection remain available; guest video setup does not hold the sharing controls. The source chooser refreshes on opening, with loading and retry feedback inside it. The host sees guests and their controllers beside a small screen preview. **Invite guests** opens file/text pairing; it opens automatically when hosting starts and closes once a guest connects. Guests open **Controllers** for devices and mapping, and **Settings** for stream/audio options and diagnostics. Panel headings stay visible while their contents scroll. Settings, permission messages and walkthroughs are also available in fullscreen. On phones, the same controls stay along the bottom and open compact panels.

Files are named **invite** and **reply**. Select one or drop it anywhere on the matching Host/Join page, or use the visible copy/paste actions. Wrong or expired files explain what to do next, and invalid imports leave an existing connection running.

The local app uses invite/reply files or copied JSON text. Configuring a hosted invite server enables temporary names and session links; configuring forwarded recovery adds recovery status when it is actually connected. An invite-server outage or expired temporary identity does not close an established game connection. Expired links are cleared when invitation access is restored; create a fresh link for new guests. Explicitly leaving, removing a guest, or stopping the game session still ends that connection. Guests can cancel a hosted join request while waiting for approval. If copying a session link is blocked by the browser, the app selects it for manual copying. There are no manual session ID/key or resume fields. After reloading the host, start a fresh session and send fresh invites.

To share part of a screen or window, choose a source, then click **Select an area…** and drag a rectangle over the preview. Confirm with **Share selected area**. Pixel coordinates are under **Exact area dimensions**. **Share full source** removes the crop. Audio keeps its selected app/system scope; cropping the picture does not crop sound. On Windows, a cropped native window can accept separately approved mouse and typing; mouse coordinates stay within the rectangle. Other cropped shares are view-only for desktop input. Game controllers stay connected. Native capture crops before encoding; browser capture uses a canvas crop and can require more resources.

For extra host views, open **Settings > Screen & audio > Additional screens & windows** during a session. Layout icons appear for guests only when two or more views are shared: single view, grid, side by side, stacked top/bottom, or a large view with a strip. Previous/next arrows switch windows in single-view mode, including fullscreen. Click a tile to feature it; the same layout controls work in fullscreen. Each view can also open in its own viewing window. Tiles and pop-outs reuse a view’s stream. For native windows, the host can enable **Allow window control** separately on each added window. Select a tile to direct approved mouse/typing there; typing requires that window to be in front on the host. Browser-picked extra views and pop-outs are view-only. **Stop desktop control** revokes every window’s permission. Each selected source consumes capture/encoder resources; encoding starts when a guest watches it.

One invite connects a whole TV/computer. For three people at the guest TV, each presses a button on their own gamepad; three independent controllers are added automatically. The host sees controller names, player assignments and paused/disconnected states beside each guest. Assign the virtual gamepads inside the game or emulator when needed. Local guest input blocking is released before hosting and cannot be reacquired by another Join tab in the same local app while a host session is active.

Browsers may hide connected gamepads until a controller button is pressed or a stick is moved while the app is focused ([Gamepad API](https://www.w3.org/TR/gamepad/)). The mapping device list updates automatically when controllers become visible, without changing the selected device or unsaved bindings. Detection does not reserve a player spot; press-to-join enrolls controllers only during a connected Play session, outside the mapping editor. Native input lists devices through the local helper and requires its separate setup and selection.

To switch whose game is being played, click **Make host** beside a connected guest. They accept, everyone reconnects to that computer automatically, and the new host chooses a screen/window or continues with controllers only. Existing voice and camera connections stay open. The old screen share stops and desktop mouse/typing permissions start off on the new host. The recipient must run the local app with a working host controller driver; a guest using only a hosted website cannot take over. Declining, cancelling or failing preparation keeps the original session running. Old invitations end with the previous host; create fresh invitations on the new host for additional guests.

Each detected controller has a **Map** button that opens its own layout. Guests can also open **Controller & keyboard mapping** for an emulator-style editor. Select the keyboard or a connected controller, choose an Xbox/XInput, PlayStation/HID, Switch Pro or generic template, then click controls to capture keys, buttons and stick directions. Live stick displays and trigger meters help test the layout. Gamepads have a saved deadzone per device; keyboard players can start with arrows/D-pad or WASD/left stick. **Save layout** remembers the device mapping in that browser, with optional named profiles to load later. Gameplay input pauses while editing. Templates use browser-standard button positions; the actual virtual controller format is selected by the host. Keyboard stick/trigger inputs are digital. This menu does not grant desktop typing permission. Browser keys work while the picture has focus; native exclusive keyboard sharing uses the same layout and requires its separate setup.

Gamepad sharing stays active when another window is in front by default. Turn off **Keep my gamepad active while using Discord or another window** to pause browser gamepad input when this app loses focus; your choice is remembered in this browser. Keyboard controls still require the picture to have focus.

Use **Fullscreen** to fill the display. In browsers that fullscreen the game panel, move the mouse or focus a call button to show its controls; they fade while playing. **Refresh picture** reconnects picture and sound while controllers stay connected. With desktop or exclusive input active, **Pause all input** releases held controls and selected native devices while keeping the video call open. Resume controllers or enable mouse/typing again when ready.

Windows setup asks separately about optional HidHide controller blocking and Interception keyboard/mouse blocking, remembering each answer. Interception has a [known unplug/replug bug](https://github.com/oblitum/Interception/issues/25) that can disable a keyboard or mouse until Windows restarts, even with the app closed. Focused browser keyboard/mouse sharing works without it; Windows shortcuts may still act locally. Choose **No** to use regular sharing; install later with **09-Guest-Exclusive-Setup**. Choose **Yes** to prepare blocking and see a restart reminder after installation. Your choice is remembered; accepted setup skips repeated checks during the current Windows boot and checks again after restarting. **Block local controller input** is on by default after accepting HidHide setup. It reserves connected controllers before a call; press a button on each controller to join a player after connecting. Background play stays on. Turn blocking off to use controllers in local apps too. The **Share controllers** switch is visible in Controllers before and during a call. Turning it off, pausing controller sharing, or choosing Pause all input stops forwarding held controller input and releases local blocking. Automatic scans and button presses do not re-enable sharing; turn the switch back on when ready. Your blocking preference is kept for that next use. Ending a call keeps the reservation while Join stays open with Share controllers enabled; switching to Host, closing Join or turning blocking off releases it. Hosting always releases local isolation, including reservations from other local tabs; only the current host creates and receives the remote gamepads. Keyboard/mouse blocking requires device selection, an explicit Start action and a live host connection. Linux uses evdev permissions; macOS uses Input Monitoring and per-device HID access. See [setup, recovery and validation limits](system/docs/guest-device-isolation.md).

The host can **Remove P…** for any claimed controller. Guests can **Remove my controller** for their own. Removal releases its held input and frees its native device/spot without disconnecting the computer or video. Pausing sharing neutralizes inputs but keeps the spots. Unplugging a controller removes it in press-to-join mode; a fresh button press can claim a free spot again. A held button does not immediately rejoin after removal.

Incoming controllers are brand-agnostic: browser-detected Xbox, PlayStation, Switch Pro and generic pads use standard layouts or saved custom mappings. Face buttons are described by position so Nintendo/other printed letters do not force an Xbox layout. This is gamepad control mapping, not raw forwarding of every proprietary feature or every specialized HID device.

Windows uses **Automatic** output by default. It uses available XInput slots, then adds HID gamepads for more players. Games must support the resulting device types. **Advanced controller setup** offers optional overrides:

- **Xbox / XInput:** broad game compatibility; four XInput slots total, shared with other local XInput devices. This is an output/API limit, not a Windows-wide gamepad or guest-brand limit.

- **HID gamepads (PlayStation layout):** allows larger groups when the game/emulator supports SDL, DirectInput or HID controllers. Press-to-join adds players as needed, without a fixed application controller cap; OS, driver and game limits still apply. Eight actual Windows HID devices have been tested through WebRTC.

Manual reservation is available by turning off **Press-to-join** in advanced setup. `PLAYER_COUNT` is the default for console/manual hosting; the browser can choose within the selected output’s limit. `WINDOWS_CONTROLLER_TYPE=auto` is the Windows default; `x360` or `ds4` forces a compatibility mode if a particular game needs it.

The in-app **?** button offers matching host/guest guides for **Play together (controllers)**, **Play together (keyboard & mouse)**, **Control a computer**, and **Connection help**. The controller guide covers any number of people per guest computer. Keyboard/mouse play sends approved desktop inputs to the game; **Use keyboard & mouse as a controller** in the controller guide instead maps keys to a virtual gamepad. No public website or router changes are required for manual pairing when a direct route or configured TURN relay is reachable. STUN alone cannot connect every network.

The interface uses the supplied WebRTC Pad design system, bundled Inter fonts, a permanent host preview sidebar, and a responsive session grid. On phones, bottom tabs separate the game/screen, controller controls, voice, and settings. Walkthroughs open the tab containing the highlighted control.

Settings opens short sections instead of one long list: **Screen**, **Guests & access**, **Voice**, and **Connection** on the host; **Stream**, **Voice**, and **Connection** on the guest. Arrow keys switch settings tabs. Guided help reveals the correct section automatically. The chevrons beside Mic and Camera open their device settings directly. Icon hints and button names follow the current action, such as muting an active microphone.

On phones, the call bar keeps seven familiar actions within reach. **More > Stream > Fullscreen** opens the game fullscreen; **More > Voice > Camera settings** opens camera options. Panels follow the actual header height, including when the mode switch wraps. Guest **More** menus open as compact popovers and close after an action, an outside click, or Escape. These controls reuse the existing streams and do not start or replace capture.

## Setup checks and call helpers

Setup shows an actionable controller warning only if controller support needs attention. Choose optional picture and audio directly in the source controls. Under **Keyboard & mouse**, approve desktop access before starting, or change it later in **Settings > Guests & access**. Those choices apply only when the session starts; changing the source, ending the session, or switching to Join before starting clears them. Switching to Join also releases an unused screen/audio preview. Controller-only, audio-only and remote desktop sessions all use the same startup page.

Open **Controllers**, then expand **Test** on a device to see its live buttons and sticks. The test samples local input on each display frame and stops drawing when closed or hidden; it does not wait for network or video updates. Native controller-only blocking rescans after a physical disconnect and restores the device card when it reconnects, even under a new device ID. Keyboard and mouse grabs still require explicit selection and approval. The host sees **controllers playing**, **controllers paused**, **Waiting for a controller button**, or **Watching** beside each guest. Click that status to show or hide only that guest’s controller cards.

During a brief connection interruption, held inputs are released while player assignments are retained. A reconnect overlay appears immediately and offers **Connection help** after 15 seconds. Existing automatic recovery uses an available call or configured backup signaling route; a broken manual connection without a working route may still need fresh invite/reply files. Desktop input is paused rather than holding keys or mouse buttons through an outage.

Mic device, output, voice quality/noise settings, camera device/size/frame rate, guest picture limits, and tile layout are remembered in this browser. Remembering a device never starts capture: microphone, camera, screen selection and desktop-control approval still need your action. Saved controller mappings and host stream settings continue to work as before.

**Settings** includes a live mic level and **Play test sound** for the browser’s sound output. The mic meter does not play your mic back, and stops measuring while hidden. System-audio sharing warns when it can capture the call’s own voices. **Join and leave sounds** is optional and off by default. Controller joins get a brief visual confirmation; animations respect reduced-motion settings.

On the host, a guest’s **More > Check guest view** requests a small snapshot of that guest’s received game picture and readings for resolution, frame rate, buffering, decoding and audio delivery/playback. It does not capture the guest’s local desktop or camera, start a return stream, or save pictures. Requests are bounded and throttled; closing the check releases its snapshot. The thumbnail is reduced in size, so use the readings to judge the original stream. Guests receive a brief notice when checked.

**Having trouble?** under **?** or **Settings** offers connection, picture/sound and controls help, with a relevant action and **Save diagnostic file**. The diagnostic file includes the selected issue and the existing redacted connection journal; it excludes addresses, secrets, device names, chat and input contents. The helper also works inside the fullscreen call.

## Call chat

Click **Chat** for floating message bubbles and an input over the call, including fullscreen. Empty space around the bubbles lets you keep interacting with the picture. New messages briefly appear when chat is closed; click one to reply. The message box expands as you type. Enter sends, Shift+Enter adds a line, and Escape closes chat. Keyboard-to-controller input pauses while typing a message.

Messages stay in memory for this call only: the latest 100 messages, up to 1,000 characters each. The host shares that recent history with new joiners and preserves it when switching hosts. Stopping or leaving clears your chat. Messages use a separate reliable WebRTC channel at low priority; no chat files or server-side message storage are created.

**＋ File** offers a file to the call. Recipients click **Receive**, then **Save file**; nothing is automatically downloaded, opened or written to the host's disk. Files can travel between guests through the host's separate file channel. Each file is limited to 64 MB, with one incoming download at a time and a 128 MB received-file cache. Transfers are paced at up to 256 KB/s each with bounded buffers; source uploads yield when controller queues or fresh video-congestion measurements are high. Cancel or remove a file in chat. Available offers are shown to new joiners while the sender remains connected. Leaving, ending the call, disabling file sharing, or switching hosts clears file offers and transfers; share files again after a host switch. Downloaded copies remain wherever the recipient saved them.

Under **Guests can share → Chat files & clipboard**, the host can turn file sharing off. **Clipboard text sharing** is separate and off by default: **Send clipboard** explicitly reads and offers up to 8,000 characters, and recipients explicitly choose **Copy**. Received text never silently replaces the clipboard. Files and clipboard contents are not added to diagnostics or persisted as chat history.

## More call conveniences

**Settings → Connection → Test this connection** checks local ICE routes and whether a configured TURN relay can allocate a route. It does not interrupt an existing call. A successful local relay check does not guarantee the other computer's network can connect.

**Map → Calibration & portable profiles** imports/exports JSON layouts and measures stick centers/ranges and analog trigger ranges. Release sticks, start calibration, rotate them fully and pull the triggers, then finish and save. Importing a layout does not grant desktop permissions. In controller Advanced settings, **Remember this controller order** orders preselected devices on future joins; controllers that were not selected still join in button-press order. Identical devices may need their order saved again if the browser changes their indices.

Controller vibration travels back to the corresponding guest controller from Windows ViGEm XInput/HID outputs. Browser vibration depends on the controller/browser; the Windows native SDL reader also supports it. It is best effort, can be disabled in controller Advanced settings, and does not imply support for every proprietary haptic effect or native Linux/Mac force-feedback backend.

**Microphone & voice settings** adds per-person volume, a configurable **Push to talk** key, and optional game-sound ducking while someone speaks. Browser push-to-talk requires this app to be focused; releasing the key or switching away closes its gate. Voice remains separate from game sound. No microphone starts just because a preference is saved.

When the host approves system-mouse control and its backend supports relative movement, guest **Mouse & desktop controls → Lock mouse for games** enables relative input. **Escape**, switching away, or host permission revocation releases it. Windows supports enforced window and desktop scopes; Linux X11/Wayland and Mac relative mode use approved desktop/screen access. macOS implementation still needs hardware validation. Games that reject synthetic input may remain incompatible.

**Screen & audio → Session presets** saves named quality/audio settings and source preferences. **Apply settings** changes choices without starting capture. **Choose saved source…** explicitly selects the source or opens the browser chooser. Presets never restore desktop permissions, device grabs, credentials or microphone/camera activation.

## Cameras, voice and diagnostics

**Before joining**, the compact **Join with** card shows selected controllers, camera preview status, and microphone choice. Open a device section to configure it in that same card; the same controls move into the call menus after connecting. Selected controllers join automatically with a Play invite; unselected devices join when a button is pressed after connecting. Spectator invites never assign controllers. Camera preview is marked private until connected and permitted by the host. Microphones stay off until explicitly turned on. Opening settings never starts capture.

The host chooses **Guests can share → Screens / Cameras / Microphones** before starting, or changes these under **Settings → Guests & access** during the session. These are separate permissions and start enabled; each guest’s own screen, camera and mic still start off. Disabling guest cameras stops camera transmission and leaves a private preview. Disabling guest microphones stops their microphone captures; guests can still listen. Re-enabling microphones requires guests to turn their own mic back on. Game screen/audio sharing and controllers are independent of these permissions.

Guests click **Share screen** to choose a window or screen in their browser’s sharing dialog. Optional sound depends on the browser, operating system and selected source; window audio may be unavailable. The chevron beside Share screen opens live quality controls: picture size, frame rate, upload budget, motion/text priority and automatic adjustment. Defaults are 1080p at 60 fps with an 8 Mb/s upload budget shared across viewers. Automatic adjustment lowers screen quality when gameplay buffering, decoding, loss or network delay rises, then recovers gradually. Manual mode keeps the chosen limits while browser congestion control remains active. Each additional viewer uses a separate peer stream, so total upload and encoding cost increase with the call size. Guest capture currently uses the browser; the host’s existing native capture remains available separately.

**Guest screen limits** sets call-wide size, frame rate and upload ceilings. A guest’s **More → Screen sharing** menu can lower their limits or stop their share separately. Turning screen permission off ends that capture, including a pending chooser; allowing it again requires the guest to choose a source again. Screen shares join **Single view**, **Grid**, **Side by side**, **Stacked** and **Featured** layouts, including fullscreen. Click a screen to feature it, or use the previous/next buttons in single view. **Streamer** places each screen owner’s camera inside their screen, or shows an avatar while their camera is off. It replaces the separate camera strip. Drag an overlay to move it or its corner handle to resize it; arrow keys work when focused. Drag the gaps between tiles to resize columns, rows, camera strips and the featured strip. Each template remembers its sizes and Streamer overlay positions in this browser, separately for host and guest. The small **Reset layouts** button beside the template icons restores all default sizes and overlay positions. Hover a camera tile or overlay for quick mic/camera controls; on touchscreens they stay visible. Your own buttons toggle your microphone/camera. Other people’s buttons mute or hide them **for you**. Personal voice mute and screen-audio mute stop the sender’s audio track to that endpoint, while other listeners continue receiving it. Camera hiding similarly stops that camera’s video to your endpoint. Unmuting restores the track on the existing connection. The host has these personal controls as well as separate **for everyone** moderation under People. These controls also work in fullscreen and only change your local view; they do not restart capture or grant input access. Cameras stay small beside shared screens. Screen tiles have individual sound controls and do not grant desktop control of the sharing guest. Controller input remains independent. Active guest shares stay connected through **Make host**; ending the call releases all screen captures.

**Camera** on either computer shares a webcam with the call. Cameras start off; watching other people never opens your own camera. The settings button next to Camera chooses a device, picture size and frame rate independently of the game stream, with 480p at 24 fps as the default. Changes apply during the call. Camera upload is capped across recipients and automatically reduces picture size, frame rate and bitrate when game buffering, loss or network delay rises; recovery is gradual. Camera video has no sound: use **Mic** for conversation. Camera thumbnails sit beside the game, support fullscreen, and join the guest layout icons alongside shared windows. Camera tiles never grant desktop input. Turning a camera off or ending the session releases its capture. Existing cameras and voice stay connected when switching hosts.

After connecting, use **Join voice** or **Listen only** to talk without a separate call app. Microphone selection, mute, noise/echo controls, listening volume, and automatic quality adjustment are under **Microphone & voice settings**. Voice stays separate from game sound and controllers. If sharing whole-system audio, choose game-only audio or a separate output for voices to avoid sending the call back to guests.

Optional **Diagnostics & charts** uses `uplot-webgpu` for a compact selectable chart with current controller delay, video buffering/decoding, frame rate, bitrate, and loss numbers. Pause, reset, or save a CSV for comparisons. It reuses existing stats and loads/releases graphics only while visible; CSV works without WebGPU. The host can choose a guest or local preview. Preview controls now sit directly under the preview box. See [voice, audio quality, and diagnostics](system/docs/voice-and-diagnostics.md).

## Platform support

Windows hosting is the most tested path. Guests on Windows, Linux and macOS use browser input and WebRTC video; native host drivers are separate.

| Host feature | Windows | Linux | macOS |
| --- | --- | --- | --- |
| Virtual controllers | Tested XInput/HID backends | Implemented; requires `/dev/uinput` access; real-device testing pending | Experimental HID backend; signing/device testing pending |
| Native capture | Implemented and tested | Requires X11; hardware validation pending | ScreenCaptureKit + VideoToolbox on macOS 13+; experimental |
| Window-only mouse access | Enforced for the selected window | X11 identity/occlusion enforcement | Public Accessibility window checks; experimental |
| Whole-screen mouse/typing | Implemented and tested | X11; Wayland portal approval when detected, compositor validation pending | Accessibility permission required; hardware validation pending |
| Desktop cursor overlay | Available | X11 click-through shaped windows | Click-through AppKit panels; experimental |
| Native guest device isolation | SDL3 + HidHide/Interception; physical suppression tested | evdev exclusive grabs; device permissions required; physical testing pending | Per-device HID seize; OS may refuse; experimental, physical testing pending |
| Native app/system audio | Available when helper/Windows version supports it | PulseAudio/pipewire-pulse playback monitors; app selection on X11, system audio on Wayland | ScreenCaptureKit app/system playback on macOS 13+; experimental |

The shared browser interface includes guided setup, optional video, host preview controls, player join/removal, saved button mappings, latency/quality controls, fullscreen and picture-in-picture where the browser supports it. These workflows are tested with Windows, Linux and macOS configurations; CI runs on all three operating systems. Chrome/Chromium is recommended for the same gamepad, capture and pop-out behavior across platforms. OS-native features retain the limits listed above.

Mouse and typing permissions start off on every host. Sharing a whole screen does not grant input access; the host must approve it separately. Whole-screen permission can also be used with the video-free mouse pad. The app shows platform notes in host settings and explains when window-only control is unavailable on non-Windows hosts.

Mac native capture/audio, window input and cursor overlays are implemented but need Mac hardware validation. Run `mac/shortcuts/07-Host-Native.command`, then follow [Mac permissions and setup](system/docs/macos-desktop.md). Screen Recording and Accessibility permissions are separate; desktop control stays off until approved.

Linux hosts detect X11 or Wayland and show only the relevant controls and help. Native X11 clicks, occlusion, resize and cursor overlays have passed isolated acceptance tests; private PulseAudio tests verify app-only audio isolation, system mixing and cleanup. See [Linux prerequisites and tested limits](system/docs/linux-desktop.md).

Run **Start-Windows.cmd**, **Start-Linux.sh**, or **Start-Mac.command** from the main folder. It installs missing dependencies and opens your saved host/join choice. Connection settings live in the top-level **`.env`** file. Setup preserves it. With no ICE settings, manual pairing uses a [catalog of public STUN endpoints](system/docs/public-stun.md) without an account. STUN helps find a direct route; restrictive networks may still need a TURN relay. Add your own Metered account, custom TURN settings or self-hosted coturn when needed. Docker, Caddy and router forwarding are separate optional steps; follow [relay hosting](system/docs/self-hosted-turn.md) and [port forwarding/recovery](system/docs/port-forwarding.md).

## Video and desktop control

To include video, select a window or screen in **Screen sharing**. Windows lists native sources directly when native capture is installed; **Choose window or screen…** opens the browser chooser, with audio when available. Both native and browser capture provide a local preview before a session; **Start a session** reuses the prepared source. On Windows, Linux X11 and supported Macs, you can check **Include audio** before selecting a source. It captures the selected application's sound for a window, or the default playback device's system sound for a screen. It starts on, but captures nothing until a source is selected. Application audio includes other windows in the same app. Linux also supports native playback audio through PulseAudio/pipewire-pulse; see [Linux desktop setup](system/docs/linux-desktop.md). With browser video, **Choose app audio instead** lets you separately select an app or system sound when the browser cannot share audio. The native audio goes directly to guests without a second browser encoding step. Selecting a source during a session switches the stream automatically. Select **No screen sharing** to stop video while keeping inputs connected.

Host resolution/frame-rate limits and each guest's requested quality are independent. Fullscreen, Chrome picture-in-picture, latency stats and automatic quality adjustment are available. Native capture uses FFmpeg and hardware encoding where available. Game picture and sound play independently to keep video responsive. See [native capture](system/docs/native-capture.md) and [gameplay latency](system/docs/latency.md).

On the guest, **Show shared screen** hides only the picture; sound and controller sharing stay on. **Stream on / Stream off** starts or pauses both picture and sound while keeping controls connected.

**Hide preview / Show preview** on the host monitor controls your local view without interrupting guests. The same option is available as **Show my screen preview** in settings; turn it off or enable **Pause my preview when I switch away** to stop local playback while guest streaming continues. Native preview also releases its local receiving connection.

Desktop typing and mouse control are separate and off by default. In-page CAUTION messages explain the scope before each side enables access. Windows, Linux X11 and supported Mac window-only mouse access follows the selected shared window; entire-screen access requires an additional host permission. Source changes preserve the chosen control mode and input options while releasing held input and rebinding to the selected supported source. Closing the window or choosing an incompatible source pauses window-only access. They share the host's real system pointer/keyboard. Guests choose keyboard-to-controller mappings in their controller panel; these control a virtual gamepad and do not grant desktop typing. Mouse buttons and wheel directions can also be bound in that editor while desktop control stays Off. Desktop control defaults to Off; choosing Shared window only or Entire desktop includes mouse and typing by default, with separate toggles to exclude either. Guests can use a mouse pad without video. Guest pointers are independent of desktop control and default off. The host can enable them when needed. Players and spectators can point and show click feedback without moving the system mouse or clicking apps. The host can hide pointers and toggle labels. Real mouse control remains separate and shares one system pointer, with colored markers still available. Supported desktop overlays follow a verified main shared source; pointer messages never enter the OS input injector. The Windows, Linux X11 and Mac desktop overlays display them over other apps and borderless games, without taking focus or intercepting clicks. Exclusive fullscreen can cover overlays; Wayland overlays are not implemented. Linux and Mac markers may appear in captured video. See [desktop control](system/docs/desktop-control.md).

## Folder layout

The three **Start-** launchers are in the main folder. `windows/`, `linux/`, and `mac/` contain instructions and `shortcuts/` for role-specific and optional tools. `system/` contains the app, native helpers, templates, scripts, tests and detailed docs. `.local/` holds private caches/configuration. `node_modules/` and `.local/` are created as needed and are excluded from the source download.

See [technical reference](system/docs/reference.md), [controller mapping](system/docs/controller-integrations.md) and [validation notes](system/docs/validation.md). Run `npm test` and `npm run check` for development checks; `npm run package` creates `releases/WebRTC-Pad.zip` without local credentials or installed dependencies.


Guest cards show their controller count plus camera/microphone state, including muted listeners. Failed connections offer one recovery action beside that guest; technical connection details and diagnostic downloads stay collapsed. Keyboard focus returns to the invoking button when a panel closes and survives controller-list updates. The guest’s status distinguishes pointers without desktop control from real shared-window or desktop input.

Stopping a session notifies guests, releases shared input and media, and returns guests to Join. A short bounded acknowledgment lets the end message arrive before the host closes its control connection. Input is frozen immediately during shutdown.


MIDI and independent keyboard/mouse streams are optional under **MIDI & app-only input**, before or during a session. The host allows MIDI and app events separately; guests choose MIDI devices and app-only keyboard/mouse sharing in Controllers. A host can forward MIDI to an existing output/virtual port. Web MIDI requires a supported browser on localhost or HTTPS; no MIDI driver is installed and SysEx is excluded. App-only keys, clicks, scrolling and normalized pointer coordinates retain separate guest/device identities and never enter the desktop or gamepad injector. These are integration events, not automatically recognized OS keyboards or mice: games need an integration, or can use the existing virtual gamepad mappings. The host can copy a private read-only localhost WebSocket URL that expires with the call. The integration guide is available at `/app-inputs`. Inputs are not recorded; call, device and permission changes release held state. Use `npm run test:app-inputs` to validate this with simulated MIDI devices and three real local WebRTC endpoints.


The local server exposes an input API at `GET /api/inputs`, session creation at `POST /api/inputs/sessions`, read-only subscriptions and separately authenticated publishing. The standalone `input-api.js` SDK provides `InputClient`, initial current-device snapshots, input/reset notifications and cleanup. The host can copy its API connection; guest controller receivers have a separate local API connection. App-only mouse, keyboard and MIDI events preserve guest/device identities; normal guest controller input is also available to host API consumers. See the in-app `/app-inputs` integration guide for routes, schema and token scopes.

Under **Share my controllers with guests**, a host can explicitly select physical controllers. Each guest opts in under **Controllers → Advanced → Receive host controllers** and chooses App-only API or a supported local virtual-controller endpoint. Native receiving pauses outgoing controller sharing to avoid virtual-pad feedback; it releases local controller blocking. App-only receiving allows both directions at once. All receiver choices default off; stop, disconnect, role changes, revocation and stale input release virtual gamepads. Drivers are not installed automatically when enabling a receiver.


Linux, macOS and Windows use the same local input API, app-only receiver and WebRTC controller routing. Native endpoints and setup help are OS-specific. Linux virtual-pad output supports both common uinput nodes and an explicit `UINPUT_DEVICE`; macOS builds target Intel/Apple Silicon and respect a custom signed HID helper. Helper failures/timeouts release devices and notify receivers. Fixture coverage includes each OS's receiver/UI/API paths, Linux report encoding and permission/cleanup failures, and Mac build architecture selection. Native Linux device behavior and macOS virtual HID authorization still require physical OS validation. See the Linux/Mac setup guides in the app.
